## Согласованная первая версия

Android 8.0+ (minSdk 26), Kotlin / Jetpack Compose. Установка APK, один магазин.
С версии 0.2.0 вход через существующего Telegram-бота, только для участников
той же группы, что разрешена в Telegram-боте. Общего кода доступа нет.
С версии 0.3.0 по запросу владельца членство проверяется только при входе.
Выданная сессия действует 30 дней без повторной проверки группы; выход из группы
больше не отзывает доступ автоматически. Данные загружаются только кнопкой «Обновить».
Главный экран: продажи, остаток FBO, в пути и
«К поставке», поиск и фильтр товаров с положительной потребностью.

Для каждого товара:

```text
К поставке = max(0, ceil(продажи / исторический_период × прогнозный_период
                         − остаток_FBO − в_пути))
```

Исторический период продаж и прогнозный период задаются отдельно, изначально по
30 дней; для обоих допустим ввод 1–365. Значения сохраняются на устройстве.
Продажи — заказанные единицы FBO + FBS, не деньги и не только доставленные заказы.
Отмены исключаются по `status` и `status_alias`. Возвращённое количество FBO и FBS
получается через `/v1/returns/list` и вычитается только из исходного отправления с
совпадающими `posting_number` и SKU. Полностью возвращённая позиция в продажи не входит.
Окно содержит выбранное число календарных дат, включая текущую, в `REPORT_TIMEZONE`
(Москва по умолчанию). Границы дат переводятся в UTC. Текущий день может быть
неполным; делитель равен выбранному историческому периоду. FBO/FBS SKU объединяются
через карточку товара.

Остатки FBS не вычитаются. Остаток — доступные единицы на складах Ozon,
сумма по складам. «В пути» — входящие поставки, а не заказы в доставке покупателям.
Запрошенные/запланированные поставки (`requested_stock_count`) не включаются.

## Источники и статус интеграции

Официальная документация: https://docs.ozon.ru/api/seller/

| Данные | Метод | Поля |
|---|---|---|
| Каталог | `/v3/product/list`, `/v3/product/info/list` | product_id, id, offer_id, sku, sources[].sku |
| Заказы FBO | `/v2/posting/fbo/list` | products[].quantity, sku, status |
| Заказы FBS | `/v4/posting/fbs/list` | products[].quantity, product_id/sku, status_alias/status |
| FBO остатки и в пути | `/v1/analytics/stocks` | available_stock_count, transit_stock_count по SKU и warehouse_id |

27.08.2026 новый отдельный ключ успешно прочитал каталог, FBO/FBS-отправления
и аналитику остатков. Владелец сверил P0001: остаток 14 шт., в пути 19 шт.
Остальные товары и пограничные состояния приёмки ещё требуют сверки.
Роли ключа: Posting FBO, Posting FBS read-only, Product read-only, Report.
Официальный сайт документации Ozon не удалось прочитать из этой среды;
формат используемых ответов проверен запросами к реальному магазину.

Если обязательные поля отсутствуют или SKU не удалось сопоставить, сервер возвращает
ошибку, а не нулевые остатки. Для SKU без строк аналитики текущий адаптер принимает
нулевой FBO-остаток; это поведение тоже требует сверки по живому магазину.
Скорость обновления аналитики ограничивается самим Ozon: время «Загружено» означает
время ответа API, а не гарантированное время изменения складского остатка.

## Локальный запуск сервера Windows

Требуется Python 3.11+ и ключ Ozon с правами чтения перечисленных методов.
Ключ не нужно передавать пользователям APK или публиковать в Git.

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements-server.txt
Copy-Item .env.example .env
```

Заполнить `OZON_CLIENT_ID`, `OZON_API_KEY` и при необходимости `REPORT_TIMEZONE`
в `.env`. Если `.env` уже существует,
не заменять его примером: сохранить текущие параметры и обновить только нужные.

```powershell
.\deployment\Start-ForecastServer.ps1
```

Проверка: `http://127.0.0.1:8000/health` (жизнеспособность процесса) и
`http://127.0.0.1:8000/api/v1/forecast?days=30` должен отдавать отчёт без сессии.
HTTP 503 с описанием недостаточных прав — не успешная проверка интеграции.

Сервер запускается с одним worker и слушает только localhost. Кэш успешной загрузки
5 минут общий для всех устройств; одновременные запросы объединяются. После ошибки
повтор не чаще раза в 30 секунд. Последний успешный снимок хранится в
`data/forecast.json` (не в Git). При неудаче обновления он выдаётся с `stale: true`
и прежней отметкой времени. После перезапуска свежая загрузка выполняется при
первом запросе отчёта, а не при запуске серверного процесса.

## Доступ с телефонов вне локальной сети

27.08.2026 для первого запуска выбран бесплатный ngrok с назначенным аккаунту
HTTPS-адресом https://quadrant-manger-tidbit.ngrok-free.dev. Покупка домена,
динамический DNS и открытие входящих портов для этого способа не нужны.
Первый запуск выполнялся отдельным бинарным файлом. После блокировки этого файла
защитой Windows пользователь установил ngrok из Microsoft Store. Для нового
ручного запуска используется установленный псевдоним (не файл в OzonSalesBot):

```bat
"%LOCALAPPDATA%\Microsoft\WindowsApps\ngrok.exe" http http://127.0.0.1:8000 --url https://quadrant-manger-tidbit.ngrok-free.dev --inspect=false --config "%LOCALAPPDATA%\ngrok\ngrok.yml"
```

Authtoken настроен пользователем локально, в репозитории его нет. Параметр
inspect отключает локальную инспекцию HTTP; трафик проходит через сервис ngrok.
Внешняя проверка подтвердила /health=200 и анонимный /api/v1/forecast=401.
Полный вход из release APK через мобильную сеть пока не проверен.

На дату настройки бесплатный план ограничен 20 000 HTTP-запросов и 1 ГБ в месяц.
С APK 0.3.0 периодических запросов проверки членства нет; пригодность тарифа
для постоянной работы всей группы ещё нужно оценить.
Условия: https://ngrok.com/docs/pricing-limits/free-plan-limits.

Пользователь подтвердил установку автозапуска API/ngrok (AUTOSTART_INSTALLED).
После установки внешняя проверка подтвердила /health=200, version=0.3.0,
и анонимный /api/v1/forecast=401. При проверочной перезагрузке API стартовал
автоматически, но ngrok завершился с кодом 1, внешний адрес возвращает HTTP 404.
При ручной диагностике Windows заблокировала запуск ngrok.exe как вирус или
потенциально нежелательную программу. Блокировка привязана к файлу в OzonSalesBot;
защита не изменялась. Версия из Store 3.39.11-msix-stable запускается вручную.
Скрытый запуск переведён на Microsoft\WindowsApps\ngrok.exe без резервного выбора
старого файла. Обновление перенесено на удалённый ПК, запуск существующей задачи
Ozon Forecast Tunnel восстановил внешний API: /health=200, version=0.3.0,
анонимный forecast=401. При второй перезагрузке ngrok снова завершился с кодом 1;
установлена логика повторов через минуту и безопасной диагностики. После запуска
обновлённой задачи внешний API снова доступен (200 для health, 401 без сессии
для отчёта). Третья перезагрузка подтвердила автоматическое восстановление
после повтора, но первая попытка получила ERR_NGROK_9040 — запрет исходного IP
со стороны ngrok. См. https://ngrok.com/docs/errors/err_ngrok_9040.
Сетевые настройки не менялись. Остановка повторов при 9040 установлена удалённо
из ozon-tunnel-policy.zip: CheckOnly прошёл, после перезапуска туннеля 27.08.2026
в 16:40 МСК внешний health вернул 200, а отчёт без сессии — 401. Перезагрузка
в 17:10 подтвердила запуск API, но туннель снова получил 9040 и остановился.
Внешний доступ после этой перезагрузки не восстановлен. Для постоянной работы
необходимо подключение, разрешённое провайдером; скрывать источник или обходить
его ограничения эта настройка не должна.

### Автозапуск Windows (0.3.0)

Пользователь подтвердил автоматический вход Windows без пароля. Установщик
`deployment/Install-ForecastAutostart.ps1` создаёт две отдельные задачи:
`Ozon Forecast API` и `Ozon Forecast Tunnel`. Триггер — вход текущего пользователя,
права Limited, без сохранения пароля. Повтор при сбое — через минуту, до 999 раз.
Установка задач подтверждена пользователем и удалённым экраном. Первый перезапуск
проверил запуск API; сбой туннеля устранён переходом на Store-версию. Запуск задачи
с обновлённым кодом проверен, повторная перезагрузка выявила сбой туннеля
(см. ANDROID-VERIFICATION.md).

Перед установкой остановить только вручную запущенные API и ngrok, сохранить
резервную копию заменяемого кода и распаковать архив обновления в OzonSalesBot.
Бот, его .env, .env.forecast и настройки ngrok в архив не входят и не заменяются.
Установщик сначала проверяет файлы, ngrok config, свободный порт 8000 и совпадение
имён задач; чужие задачи с такими же именами не перезаписываются.

```powershell
.\deployment\Install-ForecastAutostart.ps1 -CheckOnly
.\deployment\Install-ForecastAutostart.ps1
```

Pythonw запускает API без консоли, с .env.forecast и локальным адресом 127.0.0.1:8000.
Туннель запускается скрыто, с явным путём к существующему ngrok.yml и inspect=false.
Windows Job Object закрывает дочерний ngrok при остановке его задачи. Файлы
logs/forecast-api.log и logs/forecast-tunnel.log ограничены 1 МБ с тремя архивами;
тела HTTP-запросов и сырые stdout/stderr ngrok в журнал не записываются.
Установленная версия сохраняет только ERR_NGROK-коды и повторяет запуск через
60 секунд после выхода дочернего процесса. При отказе ОС в запуске повторы
прекращаются, записывается требование ручной проверки.
Автозапуск не меняет HAPP, бота, пароль, параметры сна или маршрутизацию Windows.

На компьютере работает HAPP. Изменение его маршрутов может оборвать AnyDesk;
не отключать VPN и не менять сетевые параметры без отдельной проверки.
Никакие порты, настройки роутера, VPN или брандмауэра этой разработкой не изменяются.

**Историческое примечание:** ограничения доступа в версиях до 0.5.6 больше не действуют.
Сервер 0.3.0 проверяет действительность Telegram-сессии; членство проверяется при её выдаче.
На reverse proxy нужно ограничить размер тела запросов (например, 16 КБ для
`/auth/*`) и частоту запросов. Не записывать Authorization, тела запросов входа
и URL Telegram Bot API в журналы. Встроен лимит 20 новых входов в минуту
на процесс и 1000 активных запросов входа; публичная защита от DoS требует proxy.

## Прежний вход через существующего Telegram-бота (до 0.5.6)

1. Приложение получает одноразовый запрос входа сроком на 5 минут.
2. Пользователь открывает личный чат бота, нажимает «Начать», сравнивает шестизначный
   код на двух экранах и нажимает «Подтвердить мой вход».
3. Бот проверяет членство и подтверждает запрос в локальной SQLite-базе.
4. Приложение получает сессию (30 дней) через отдельный секрет запроса,
   который не передаётся в Telegram-ссылке. Код на экране сам по себе не является паролем.
5. Сервер проверяет только действительность выданной сессии на запросах отчёта,
   в том числе после долгой загрузки. Повторных запросов членства к Telegram нет.

Бот должен быть администратором группы: это требование надёжной проверки других
пользователей через [getChatMember](https://core.telegram.org/bots/api#getchatmember).
В существующей группе статус бота administrator подтверждён запросом 27.08.2026.
Ссылки входа используют [Telegram deep linking](https://core.telegram.org/bots/features#deep-linking).
Начиная с APK 0.2.1 кнопка «Открыть Telegram» преобразует строго проверенную
серверную ссылку в `tg://resolve?domain=...&start=...` и открывает установленный
клиент Telegram напрямую. Страница t.me в браузере для этого не нужна.
Имя бота и полный одноразовый параметр сохраняются; дополнительные параметры,
чужие домены и произвольные intent-ссылки не принимаются.
Если клиента Telegram нет, приложение показывает ошибку без перехода в браузер.
Формат: https://core.telegram.org/api/links#bot-links.
Статусы left/kicked и restricted с is_member=false не получают новую сессию.
Если Telegram недоступен, новый вход невозможен; уже выданная сессия продолжает
работать. Удаление из группы не отзывает старые сессии. Сессия прекращается при
выходе из приложения, по истечении 30 дней, после ротации токена бота или смены группы.

### Обновление работающего бота — отдельный шаг

Вход требует обновлённого `ozon_sales_bot`, одного уже существующего процесса
long polling и Android API **на одном компьютере** с общей SQLite-базой.
Не запускайте второй процесс бота с тем же токеном: они будут конфликтовать.
API сам не вызывает getUpdates и не меняет webhook.

У обоих процессов задайте `FORECAST_AUTH_DB` с одинаковым абсолютным локальным
путём, например `C:/OzonServer/data/android-auth.sqlite3`. Относительный путь
работает только при одинаковом рабочем каталоге. Не размещайте SQLite на сетевом диске.
Бот без переменной FORECAST_AUTH_DB сохраняет прежний режим и не подтверждает входы Android.
Перед обновлением сделайте закрытую резервную копию кода, .env и баз данных,
остановите существующий процесс бота через его штатный механизм, обновите код
и установите зависимости `requirements.txt` и `requirements-server.txt`.
Сохраните текущие значения .env и добавьте FORECAST_AUTH_DB; не заменяйте .env примером.
Затем запустите ровно один экземпляр бота и API. На рабочем удалённом компьютере
обновление и перезапуск выполнены пользователем 27.08.2026; успешный вход и
авторизованный ответ API подтверждены пользователем через проверочную команду.

## Android

С версии 0.2.2 внизу экранов приложения отображается «© ESI.Company».
С версии 0.2.3 заголовок, настройки периода, итоги, поиск и фильтр прокручиваются
вместе с карточками товаров в одном списке. Карточки остаются отдельными lazy
элементами со стабильными ключами; подпись ESI.Company остаётся внизу экрана.

В «Сервер» вводится HTTPS-адрес, полученный после сетевой настройки. Начиная с 0.3.0
открытие, возврат в приложение и завершение входа не загружают отчёт. Только кнопка
«Обновить» отправляет серверу выбранные исторический и прогнозный периоды и
запрашивает данные (снимок для того же исторического периода может использоваться
из кэша до 5 минут). Изменение полей само по себе не меняет уже показанный расчёт.
Отчёт хранится в оперативной
памяти и сохраняется при сворачивании и временной ошибке обновления. Ошибка
показывается рядом с прежней датой загрузки; не выдавать прежние данные за свежие.
После перезапуска процесса нужно нажать «Обновить». На диск отчёт не сохраняется;
старый кэш 0.1.0 удаляется. Выход, смена сервера и ответ 401/403 очищают отчёт и сессию.
Сессионный токен зашифрован AES-GCM с ключом Android Keystore и привязан к адресу
сервера. Резервное копирование выключено. С версии 0.3.1 по просьбе пользователя
снимки экрана и превью в списке недавних приложений разрешены (FLAG_SECURE убран).
FLAG_KEEP_SCREEN_ON удерживает экран включённым, пока окно приложения видно;
после сворачивания действует обычный тайм-аут Android. Кнопка питания не блокируется.
Сбой Ozon может дать старый серверный снимок с предупреждением при действительной сессии.

Debug-сборка допускает HTTP только для localhost/127.0.0.1/10.0.2.2 (эмулятор).
Release требует HTTPS и не отключает проверку сертификатов. Перенаправления не
следуются автоматически. В APK нет ключа Ozon и адреса конкретного магазина.

### Сборка

JDK 17+ (проверяется с JDK 21), Android SDK 36, Build Tools 36.1.0.
Задать `JAVA_HOME` и `ANDROID_HOME` либо путь SDK в исключённом `android/local.properties`.

```powershell
android\gradlew.bat -p android assembleDebug testDebugUnitTest lintDebug
android\gradlew.bat -p android assembleRelease
```

Если путь проекта содержит кириллицу, JVM-тесты Gradle на Windows могут завершиться
`ClassNotFoundException`, хотя APK собирается. Используйте копию исходников в ASCII-пути:

```powershell
.\deployment\Build-Android.ps1
```

Скрипт создаёт отдельную папку сборки внутри `%LOCALAPPDATA%/OzonPlanBuild`, не меняет
и не удаляет исходный проект. APK копируются в `outputs/android`.

Release по умолчанию unsigned. Для распространения нужен отдельный ключ подписи
и `apksigner`; ключ и пароль хранить вне Git, сохранить резервную копию. Все обновления
приложения должны подписываться тем же ключом. Debug APK — только для проверки.

Для подготовленной сборки ключ создан локально в `.local/signing`. **До удаления
рабочей папки сохраните эту папку в закрытом резервном хранилище**; она содержит
ключ и пароль. Не передавать её пользователям приложения. Повторная подпись:

```powershell
python deployment/sign-apk.py --jdk C:/path/to/jdk --sdk C:/path/to/Android/Sdk
```

Подписанный APK: `outputs/android/ozon-plan-<версия>.apk`. Номер Android-приложения,
API и пакетов берётся из общего `version.properties`. Первый запуск показывает настройку
адреса сервера; тестовые данные из проверки эмулятора в APK не встроены.

Начиная с 0.5.3 приложение при открытии проверяет обновление отдельно от данных Ozon
(не чаще одного раза в 6 часов), скачивает APK с авторизованного сервера и сверяет
размер и SHA-256. Для публикации новой версии сначала соберите и подпишите APK,
затем создайте `python deployment/package-server.py` и установите весь пакет на
сервер: `updates/ozon-plan.apk` должен соответствовать `version.properties`.
Нельзя публиковать новый `version.properties` со старым APK. После загрузки
приложение предложит установку; разрешение установки из этого источника и само
подтверждение установки выполняет пользователь в Android. Версию 0.5.3 на ранее
установленные приложения нужно установить вручную один раз.

С 0.5.4 продажи в раскрывающемся списке относятся к кластеру доставки покупателю
(`financial_data.cluster_to`) для FBO и FBS. Остатки и товары в пути остаются
привязаны к кластеру хранения. Если Ozon не указал кластер назначения, такие
продажи показываются отдельно как «Кластер назначения не определён».

С 0.5.5 APK скачивается частями по 512 КиБ с проверкой каждого диапазона,
повтором при обрыве и итоговой проверкой SHA-256. Это снижает риск сбоя при
передаче большого файла через туннель. Если установленная 0.5.3 или 0.5.4
уже не может скачать обновление, 0.5.5 нужно установить вручную поверх неё.

С 0.5.6 приложение не запрашивает Telegram-вход и не передаёт токен серверу.
Серверные маршруты `/auth/*` удалены; `/api/v1/forecast`,
`/api/v1/warehouse-stocks` и `/api/v1/update*` общедоступны.

## Прогресс обновления (0.6.4)

Карточка обновления показывает текущий этап: проверка версии, скачивание, проверка целостности и сохранение APK. При скачивании отображаются реальные полученные байты, процент и объём в МБ; повторная попытка обозначена отдельно. После проверки файла отображается готовность 100%. После нажатия установки показано, открыты ли настройки разрешения или установщик Android. Прогресс самой установки контролирует Android, приложение не показывает вымышленный процент установки.


## Рентабельность (0.7.0)

Период — даты создания заказов FBO и FBS (1–365 дней, включительно).
Для выбранных отправлений загружаются все доступные на момент обновления
начисления через `/v1/finance/accrual/postings` пакетами по 200 отправлений.
Тип комиссии за продажу определяется по имени SaleCommission из
`/v1/finance/accrual/types`. Дебет комиссии соответствует продаже, кредит —
сторнированию продажи; цена продавца за единицу умножается на количество.
Неоднозначные суммы/валюта и несогласованные количества приводят к ошибке,
а не к правдоподобному нулю. Свежие заказы могут не иметь начислений.

Учитываются только строки с точным совпадением номера отправления и SKU
из состава этого отправления. Строки без SKU или с неподтверждённым SKU
исключаются и считаются отдельно. Общие расходы магазина не запрашиваются
и не распределяются. Возвраты удержаний уменьшают расходы.

Средние расходы = удержания / заказанное количество.
Прибыль = выручка за вычетом возвратов − удержания − последняя себестоимость
× (выкуплено − возвращено). Маржинальность = прибыль / выручка × 100%.
Без себестоимости прибыль не вычисляется; при неположительной выручке
маржинальность не вычисляется. Налоги и внешние расходы не включены.

Общая себестоимость и снимки отчётов хранятся в `data/profitability.sqlite3`.
Изменение себестоимости не обращается к Ozon. Редактировать могут все
пользователи сервера, как согласовано владельцем. Не удалять БД при обновлении.
Android сохраняет последний отчёт отдельно для каждого адреса сервера.
Обращение к Ozon происходит только по кнопке «Обновить»; одинаковый период
кэшируется на 5 минут. После ошибки применяется задержка не менее минуты.

Официальная документация: https://docs.ozon.ru/api/seller/#operation/GetFinanceAccrualPostings


### Исправления 0.7.1

Период можно задать числом дней (1–365): конец — сегодня, начало — сегодня
минус N−1 дней. При ручном изменении дат поле дней очищается.
Финансовые запросы разделяются паузой 2 секунды. При 429 сервер повторяет
тот же запрос с увеличением паузы 2, 4, 8, 16, 32 секунды и учётом Retry-After.
Уже загруженные заказы и пакеты сохраняются в таблице pending на 15 минут;
следующая попытка продолжает с незагруженного пакета. Полный отчёт не
заменяется неполным. Нулевая комиссия за продажу допускается; отрицательная
цена в сторно уменьшает выручку. Android ожидает финансовый ответ до 10 минут.

### Версии 0.7.2–0.7.3

Порог стоимости = средние удержания на заказанную единицу + последняя себестоимость.
При отсутствии себестоимости или заказанных единиц отображается прочерк.
Перед списком товаров отображается «Заработано за период» — сумма прибыли всех
товаров отчёта, независимо от поискового фильтра. С версии 0.7.4 товары без себестоимости исключаются из итога; рядом отображается
количество учтённых и исключённых товаров. Нулевая себестоимость считается заданной.
Оба показателя пересчитываются после изменения себестоимости без запроса к Ozon.

### Общие расходы Ozon — 0.7.6

Из общей прибыли товаров с заданной себестоимостью вычитается полная сумма общих расходов магазина за выбранные даты начислений. Расходы показаны отдельным списком по видам; положительные корректировки уменьшают расход. В карточки товаров они не распределяются. Начисления POSTING и ITEM с номером заказа не вычитаются повторно. Общие начисления получаются из /v1/finance/accrual/by-day с пагинацией, дедупликацией accrual_id, паузами и сохранением промежуточного результата для продолжения после ошибки. Старый отчёт без общих расходов помечается как не учитывающий их; нужен ручной «Обновить». Налоги и внешние расходы не учтены.

### Длительные отчёты — 0.7.7

Android запускает POST /api/v1/profitability/jobs с датами, затем короткими GET-запросами /api/v1/profitability/jobs/{job_id} получает статус, этап и готовый отчёт. Это устраняет зависимость длительного отчёта от тайм-аута одного проксируемого соединения. Одновременный запуск того же периода использует существующее задание; другой период возвращает 409. При остановке API задачи отменяются, промежуточные данные остаются в SQLite для повторной попытки. Веб-ресурсы подключаются только при наличии папки web, их отсутствие не блокирует API.

### Повторное использование дневных расходов

Полные дневные суммы общих расходов хранятся в expense_days и используются для других диапазонов. Срок свежести: сегодня 5 минут; последние 7 дней 1 час; старые даты 24 часа. Повторный запрос не отменяет эти сроки: это ограничивает нагрузку на Ozon. После истечения срока день обновляется, включая поздние корректировки. Старые агрегированные отчёты не позволяют восстановить разбивку, поэтому кэш наполняется при следующих загрузках.

## 0.7.8: отчёт по датам финансовых операций

Период рентабельности определяется датами начислений и списаний Ozon. Доход разбит на оплату покупателей, баллы за скидки и доплаты Ozon; цена продавца не прибавляется повторно. Возвраты уменьшают компоненты дохода и восстанавливают себестоимость. Продаж в периоде может не быть при наличии возвратов. Поле ordered в новом отчёте означает число единиц начисленных продаж, а не заказы по дате создания; отдельная статистика созданных заказов не запрашивается. Остаточные операции, не распределённые строго по SKU/заказу, показываются отдельно и сверяются с total_amount. accounting_basis=accrual_date_v1; старые отчёты хранятся отдельно.


## 0.8.0: расчёт по выбранным заказам, как в «Марже Ozon рядом»

Текущий расчёт — `accounting_basis=order_cash_v2`. Заказы FBO/FBS выбираются
по дате создания (последние 365 дней, границы по Москве). По этим отправлениям
учитываются дневные начисления с начала периода до дня загрузки. Общие расходы
без связи с заказом учитываются только между выбранными датами.

Выручка складывается из оплаты покупателя и компенсаций Ozon (`sale_price`,
`coinvestment`, `bonus`) с количеством и знаками возвратов. `seller_price`
не прибавляется повторно. Комиссия, услуги доставки и item_fees уменьшают прибыль;
доставка при отказе не создаёт выкуп и не списывает себестоимость. Возврат продажи
уменьшает выручку и восстанавливает себестоимость. Средние удержания снова делятся
на количество заказанных единиц. Себестоимость по-прежнему общая на сервере.

Предыдущий расчёт по датам финансовых операций описан выше как история 0.7.8.
Его сохранённые отчёты не используются как новый расчёт. При наличии старого отчёта
Android и iPhone показывают предупреждение о другом принципе расчёта.

Последние 14 календарных дней загружаются заново. Более ранние полные дневные
ответы используются не дольше 24 часов. Кнопка «Полная сверка» передаёт
`full_reload=true` в фоновое задание и получает все дни заново. Незавершённая
страница не попадает в дневной кэш; готовый отчёт заменяется только после успешной
проверки. При повторной попытке свежие 14 дней загружаются снова.
